Kar-Conform tells you whether JSON outputs match their JSON Schema contract, every violation with its exact path, and whether two runs really differ or were only reformatted. It runs entirely in this page: nothing you paste is sent anywhere, and no AI judges anything.

What this actually checks (read before trusting a verdict)

In scope

  • Structural conformance to a JSON Schema contract: type, required, properties, additionalProperties, patternProperties, items (incl. tuple form), enum, const, minimum/maximum/exclusiveMinimum/exclusiveMaximum/multipleOf, minLength/maxLength/pattern, minItems/maxItems/uniqueItems, allOf/anyOf/oneOf/not, local $ref into $defs/definitions.
  • Canonical form: object keys sorted, whitespace stripped, numbers via standard JS number-to-string — so two JSON blobs that mean the same thing hash the same, regardless of key order or spacing.
  • Cross-run consistency: among the candidates that pass, are they canonically identical (stable) or do they diverge (silent drift between calls)?

Limits: what it does not check

  • It checks the common rules of JSON Schema (2020-12), not all of them. A schema that uses a rule it does not check (if/then/else, prefixItems, dependentRequired, $dynamicRef, a $ref to another file or URL, and the rest) FAILS every output with a message naming the rule and where it sits. It never passes an output against a rule it did not check. Version 1 skipped such rules silently; version 2 refuses them.
  • format is checked for email, date, date-time, URI and UUID only, each by a simple pattern rather than the full official grammar: a format failure is a strong hint, not a final verdict. Any other format name (hostname, ipv4…) is not checked, as the JSON Schema standard allows.
  • It cannot tell you the JSON is true, only that it is shaped the way the contract said it would be. {"city": "Paris", "country": "Germany"} has the right shape, two strings, and is still wrong.
  • Two outputs count as the same only if they are exactly the same data once key order, spacing and number spelling are evened out: 1.0 and 1 match, "1" and 1 do not. "Nearly the same" never counts as the same.

↻ How to reproduce this verdict without this page

  1. Validate each candidate JSON against the contract's JSON Schema keywords listed above, in any conformant validator, recording every violation as (path, message).
  2. Canonicalize any JSON value v recursively: objects → {} with keys sorted ascending by UTF-16 code unit and re-emitted as "key":canon(value) joined by commas; arrays → [] with elements in original order; strings → standard JSON string escaping; numbers → the ECMAScript Number.prototype.toString() form (reject NaN/Infinity, normalize -0 to 0); true/false/null literally. No inserted whitespace anywhere.
  3. UTF-8 encode the canonical string and take SHA-256, hex-encoded lowercase. That is the hash shown per candidate and for the contract itself.
  4. Two candidates with the same hash are, by construction, the same JSON value — independent of formatting, spacing or key order. Two passing candidates with different hashes proved the AI's output actually changed between runs, not just its formatting.

How it works

  1. Each output is checked against the schema's keywords (the supported subset is listed in SKILL.md) and every violation is listed with its path, such as $/email.
  2. Each output is rewritten in one canonical form and hashed with SHA-256, so a reformatted answer has the same hash and a real change does not.
  3. The verdict covers every output given, so drift between runs of the same prompt shows at once.

Words on this page

JSON Schema
A standard way to write down the shape an output must have: which fields, of what type, which are required.
Canonical hash
Keys sorted, spaces removed, numbers in one spelling, then SHA-256. {"b":2,"a":1} and { "a": 1.0, "b": 2 } give the same hash, so two runs that agree show as one.
Best-effort format check
An email, date, date-time, URI or UUID is checked by a simple pattern, not the full official grammar, so a format failure is a strong hint rather than a final verdict. Any other format name (hostname, ipv4…) is not checked at all, as the JSON Schema standard allows.
Kernel
The small piece of code that decides every verdict; the rest of the page only shows what it decided. Here it is the block inside this page, copied byte for byte into kernel.mjs (the file the tests run) and into the script, so all three are the same code.
SHA-256 receipt
A 64-character fingerprint of the input and the verdict. Anyone with the same input gets the same fingerprint; change one character and it changes completely.
Deterministic
No AI model, no random numbers and no clock go into a verdict, so the same input gives the same verdict on any machine, every time.
No AI judge
No language model decides anything. The verdict comes from fixed rules you can read in kernel.mjs.
Mutation gate
A test of the tests. witness makes small deliberate changes to the kernel, one at a time: for example it turns if (count > 0) into if (count >= 0), then runs the tests. Every change must make a test fail. A change no test notices has survived: it would mean no test checks what happens at that exact point. A change reviewed as equivalent cannot alter any result (both versions give the same answer for every input), and the reason is written down and checked.
CI
Continuous integration: GitHub re-runs every test and the gate on its own computers on every change, and the runs are public.
In the browser
The page does the work on your computer. Nothing you paste is sent to a server.
MIT licence

Sourced figures

Blueprint

  • One source of truth. The checking logic is the KERNEL block inside this page. build.mjs copies it byte for byte into kernel.mjs (which the tests and the mutation gate run) and into scripts/kar-conform.mjs (the one-file agent skill). CI fails if the three ever differ, so the page you use, the code that is proven and the script an agent runs are the same code.
  • Tests. kernel.test.mjs tests the kernel; skill.test.mjs runs the shipped script on its own, the way an agent platform runs it, against the expected outputs in examples/.
  • Mutation gate. witness makes one small change to the kernel at a time (a < becomes <=, an && becomes ||) and re-runs the tests. Every change must make a test fail: that proves the tests check each of those points, rather than just running the code (see Mutation gate in Words on this page). Against what you do now

  • Reading the output. A missing field or a wrong type in a long object is easy to miss.
  • A general JSON Schema library. It validates, but it does not tell a reformatted answer from a changed one between runs.
  • Asking a model to check. Its answer is not reproducible.

Security, data protection and deployment

  • The page runs entirely in your browser; nothing you paste is sent anywhere. It can be served from your own intranet unchanged.
  • The script is one file with no dependencies and makes no network calls; it runs on Node.js 20 or later, on any machine or CI runner.
  • Deterministic: no AI model, no random numbers and no clock go into a verdict, so the same input gives the same verdict on any machine. The receipt hash lets anyone re-check a result.

Where it stops, answered straight

  • Shape, not truth. An output can satisfy the schema and still be wrong.
  • A keyword subset. Remote $ref, if/then/else, dependentRequired, unevaluatedProperties and $dynamicRef are not checked, and an unknown format is ignored.
  • Formats are best effort. format checks are patterns, and pattern uses JavaScript regular expressions.

FAQ

Why the canonical hash?
Because a model can return the same data in a different order or spacing. The hash tells you whether two runs really differ.
Can an agent run it?
Yes. The same kernel ships as a one-file Node.js script (scripts/kar-conform.mjs), usable as an agent skill after every structured call.
What happens with bad, empty or very large input?
An output that is not valid JSON FAILS with the parser's message, and the other outputs are still checked. A schema rule it does not check (such as if/then/else, prefixItems, dependentRequired or a $ref to a URL) FAILS every output with a message naming the rule and where it sits, instead of passing quietly. Version 1 skipped those rules silently, so an output that broke an if/then rule came back PASS; version 2 refuses the schema. A schema file that cannot be read or parsed is refused (exit 2).
What do I need to run it?
For the page, a modern browser; there is nothing to install. For the script, Node.js 20 or later (free from nodejs.org; node --version shows which one you have): download scripts/kar-conform.mjs (one file, no dependencies, no npm install) and run it with no arguments to see how to call it.
Does it need the internet or an account?
No. The page works once loaded, and the script runs offline. Nothing is uploaded.
